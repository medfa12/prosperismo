# Prospero shader ISA compliance: 209 of 540 instructions cannot be decoded

Generated by `scripts/isa_compliance.py`; the full list is `prospero-isa-gaps.txt`. Regenerate with:

```
python scripts/isa_compliance.py > docs/prospero-isa-gaps.txt
```

Ground truth is Sony's instruction index, not AMD's RDNA2 guide - see `prospero-isa-source.md`.

The current 2026-07-31 census has 721 decoder keys. Scalar-half add, sub,
reverse-sub, multiply, min and max are no longer gaps; Sony's executable SDK
oracle and LLVM gfx1013 fixtures agree on their bytes. The family table below
is a prioritization snapshot rather than a substitute for rerunning the script.

**This is not an Astro lead.** Astro's traced shaders contain zero undecoded-opcode markers. This is
about other titles: a shader using any instruction below either refuses translation (dropped draw) or,
worse, decodes as something else and produces wrong pixels silently.

## Where the gaps are

| Family | Missing | Character of the gap |
|---|---:|---|
| `v_*` | 139 | overwhelmingly **width variants** - f16, f64, i16/u16, and packed `v_pk_*` forms |
| `s_*` | 47 | hardware-register access, relative addressing, cache control, subvector loops |
| `ds_*` | 25 | GWS/GDS, ordered/conditional operations, `mskor`, and uncommon variants; append/consume are implemented |
| `flat_*` / `scratch_*` | 9 | the FLAT/SCRATCH segments, already a known audit item |
| `buffer_*` / `tbuffer_*` | 4 | `d16` format variants |
| `image_*` | 3 | `msaa_load`, `gather4h`, and `get_lod`; BVH `intersect_ray` is implemented |

The single clearest pattern: **we implemented the 32-bit lane of the VALU and little else.**
`v_ceil_f32` decodes, `v_ceil_f16` and `v_ceil_f64` do not. Same for `v_floor`, `v_rcp`, `v_sqrt`,
`v_cvt_*`, `v_div_*`, `v_fma_*`. Any title that uses half-precision maths - which is most modern
console rendering - hits this immediately.

## Highest value first

1. **f16 VALU (43 instructions).** Half precision is pervasive in modern PS5 shaders. This is the
   largest single block and probably the cheapest, since the f32 forms already exist and the SPIR-V
   side mostly needs the 16-bit type plus `v_pk_*` handling for the packed forms.
2. **`s_getreg_b32` / `s_setreg_b32` / `s_setreg_imm32_b32`.** Shaders read hardware state (wave id,
   mode bits) through these. A shader that reads a hardware register and gets nothing is not
   recoverable by any later stage.
3. **`s_movrels_*` / `s_movreld_*` / `s_movrelsd_2_b32`.** Relative SGPR addressing - indexed
   register access. Silently wrong register selection is the worst failure mode in this list.
4. **FLAT / SCRATCH (9).** Already flagged in `ps5-shader-isa-audit.md`; pixel-shader scratch spills
   in long shaders land here.
5. **f64 VALU (28).** Rarer in game shaders than f16 but appears in compute.
6. **`ds_gws_*` and the remaining ordered/GDS operations.** Needed for geometry
   streamout and ordered work; `ds_append`/`ds_consume` are no longer part of
   this gap.
7. **`d16` buffer formats.** `buffer_gl0_inv` and `buffer_gl1_inv` now decode
   and lower to a device-scope acquire barrier; the remaining gap is the two
   templated load/store format families.

## How the comparison works, and the three ways it lied first

`scripts/isa_compliance.py` compares on a **normalised key** - lowercase, punctuation removed - so
Sony's `v_madak_f32` matches our `VMadAkF32`. Three earlier versions of this comparison gave
confidently wrong answers, all corrected by checking a claim against the source:

1. **Stem reduction under-matched.** Reducing both sides to a family stem made `buffer_store_format`
   look missing while we clearly emit `BufferStoreFormatXyzw`. Templated entries need prefix
   matching against the fixed part before the placeholder, and only those.
2. **Case sensitivity.** A Python `in` check said `v_madak` was unimplemented; a PowerShell grep said
   it was. PowerShell's `Select-String` is case-insensitive by default and matched `VMad**A**kF32`.
   Our decoder splits words differently from Sony, so the comparison must be case-insensitive.
3. **Substring matching in the wrong direction.** Allowing "our key is a substring of the Sony name"
   let a short key such as `VDiv` mask `v_div_fixup_f32`, which is genuinely absent. Only "our key
   contains the whole Sony name" is sound. This one *hid* 119 real gaps - the count went from 121 to
   229 at the time. The current count falls as proved implementations land.

Verified in both directions before publishing: a sample of reported gaps confirmed absent from
`SharpEmu.ShaderCompiler*`, and a sample of known-implemented instructions (`v_trunc_f32`,
`s_abs_i32`, `v_cmp_class_f32`, `v_rndne_f32`, `v_ceil_f32`, `v_madak_f32`) confirmed **not** listed.

## Limits

- Sony's document templates some names (`buffer_load_<dataType>`), so a templated entry counts as
  covered when we implement any concrete variant. Per-variant coverage inside those families is not
  measured here.
- The comparison is by **name**. It says nothing about whether an implemented instruction is
  implemented *correctly*, and nothing about opcode **numbers** - those live in the PDF encoding
  diagrams, which are vector drawings whose field values did not survive text extraction, and
  `pdftoppm` is not installed so the pages cannot be rendered.
- Because numbers are unavailable, a wrong opcode *number* mapping cannot be detected by this tool at
  all. The `v_dot*` family in `prospero-isa-source.md` is exactly that risk.
