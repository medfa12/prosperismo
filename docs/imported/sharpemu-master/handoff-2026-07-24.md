### ROOT-CAUSE FINDING (done 2026-07-24) — `sceAudioOut2PortGetState` out-struct
Disassembled `libsceaudioout.sprx` (NID `gatEUKG+Ea4`, fileoff 0x45f80, 808 bytes). Contract:
- **rdi packs `(contextId << 32) | portId`**; low-32 sign-checked — a NEGATIVE low-32 is a distinct
  system/aux port class handled via a separate query path (returns `0x80268009` on miss). Our impl
  treats rdi as one flat handle key — fine for HLE keying, but the neg-low-32 port class is unmodeled.
- Error codes CONFIRMED correct in our impl: null out-ptr → `0x80268001`, bad port → `0x80268009`.
- **The out-struct offset 0 is a 16-bit FLAGS/STATE bitfield, not a routing enum.** Firmware reads
  `[r14]` first, then sets/clears **bit 7 (0x80)** from a queried "active/ready" byte, and under the
  connected-state code **0x104** with a zero level-float it clears bit 0 (`and ax,0xff7e`), zeroes
  byte `[r14+2]`, and clears bit 0 of byte `[r14+8]`.
- **Our impl (`AudioOut2Exports.cs:783`) writes a routing enum `0x01` at offset 0 (bit 7 CLEAR) and
  zero-clears the whole struct first.** If SoundManager polls this and waits on bit 7 (port
  active/ready) or the 0x104 state, our value never satisfies it → the spin/assert you're unwinding.
- **Likely fix (HLE, my lane):** write offset-0 as the bitfield — set bit 7 when the port is
  connected/active, honor the 0x104 connected-state, and stop zero-clobbering bits the caller pre-set.
- **Confidence:** moderate-high that offset-0 is a bitfield with bit-7 significant; the exact bit the
  SoundManager checks needs confirming against its read site (VM / game eboot). SDK-4.00 has no
  audio_out2 header in the extraction, so the struct isn't pinned from headers — disasm only.

## UPDATE 2 (2026-07-24, after commits `8082ae7..5f5f729`) — read this before more unwind work

### The causal chain: `defaultBusses` is empty *because* ports never report ready
You are now injecting a synthetic `std::vector` element into the SoundManager singleton at
`+0x2730` from the VEH unwind (`dded509`, `9d6a79d`), because the readiness continuation walks an
empty `defaultBusses` and faults. Your own comment names the reason: *"nothing this emulator models
registers the default bus."*

**That is the same bug as UPDATE 1.** The engine builds `defaultBusses` from audio port
enumeration/state. If `sceAudioOut2PortGetState` reports every port as not-active (our impl writes
`0x01` at offset 0 with **bit 7 clear**, and zero-clobbers the struct), the SoundManager adds no bus
→ `defaultBusses` stays empty → readiness loop spins → assert → you unwind → the continuation walks
an empty vector. Fixing the port-state bitfield plausibly makes the vector populate *itself*, through
the engine's own code path, and the assert never fires.

**Recommended next experiment (cheap, high information):** set bit 7 (and honor connected-state
`0x104`) in `AudioOut2Exports.cs:783` — note it is **still unchanged**, your audio fixes landed on
`GetSpeakerInfo` / `sceAudioOutGetPortState` / Ngs2, not on this one — then boot *without* the
defaultBusses injection and see whether the engine populates the vector on its own.

### On the `defaultBusses` injection itself — keep it as a probe, not a fix
As a **diagnostic probe** it is legitimate and useful: it advances the boot past the stall and reveals
what blocks next. That's real information. But it must not be treated as the fix or shipped —
it hardcodes an Astro-specific singleton offset (`+0x2730`), a guessed 0x18 element size, and a magic
guest-address range, and it synthesizes guest C++ engine state from a CPU exception handler. It
cannot survive a game patch and generalizes to no other title. Root-cause via the contract instead.

### Your audio-layout fixes were the RIGHT method — and they proved the bigger point
`fc6a2d0` / `7b98f36` (restoring the 0x50 `SceAudioOut2SpeakerInfo`, the full `sceAudioOutGetPortState`
state, the 0x40 Ngs2 buffer-info) are exactly right: you used **the SDK as ground truth** to correct
invented layouts. That is the framework's core principle, reached independently.

It also proved the framework's thesis empirically: those layouts were silently wrong, **1038 tests
stayed green**, and only a deep manual debug found them. `docs/conformance-framework.md` now
prioritizes generating struct-layout/size conformance tests straight from the SDK-4.00 headers so this
entire bug class becomes impossible to reintroduce. Your session supplied the evidence for that.
