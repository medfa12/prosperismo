# The cold-boot sequence

> **Provenance boundary.** Sony ground truth is the shipped movie, managed
> state machine, native renderer/shaders, particle records, textures, and audio.
> `BootIntroField` and both scripts below are inherited procedural
> visualizations: their geometry, point sets, colour construction, and
> compositing are authored by this project. Injecting decoded firmware values
> into that visualizer does not make its frames Sony output or a faithful boot.
> The separate `exp/shell-boot` experiment executes NPXS40087 but has not yet
> submitted a visible frame. See `ps5-reactive-shell.md` for the unified target.

The console's cold boot is a six-second particle piece: a seed of light, a
bloom, a blue knot of curl-noise filaments over a long drift of motes, a hard
snap where the whole field changes colour, and a dispersal to black.

There are two historical host-side experiments, and this document covers both
because the second only makes sense against the first.

**Simulating it** is `tools/boot-anim/render_boot.py`. `--palette original` is
the console's own colouring, and exists so the model can be checked against the
shipped movie before anything is restyled. `--palette prism` is the
substitution: where the console's colorchange turns **gold**, it fans the hue
out into a **full prism spectrum** and splits the shaft of light with it.

**Recolouring the console's own movie** is `tools/boot-anim/recolor_boot.py`.
It is a media fallback, not native renderer execution. The measurements below
explain why it was preferred over the procedural model.

**The model does not yet reproduce the original, and the gap is structural
rather than chromatic.** Rendered in the console's own palette and measured
against the movie, every beat lands within 52 ms of 6000 ms, whole-run mean hue
is within 8.7 degrees weighted by chroma, and unfitted blue-phase mean
luminance is within 22 % rms - but the mean absolute Laplacian of luminance,
normalised by the frame's own mean, is **22 % of the reference's** through the
blue phase and 34 % through the warm one. The reference puts its light into a
compact knot of resolved ribbons over a dark frame (bright end 0.257, a fifth
of the frame lit); we spread the same light over 1.7x the area at 0.57x the
peak. The ribbons, the rendezvous line and the bokeh discs are all present as
an average and absent as features, because the particle counts here are about
an order of magnitude short of what the choreography needs. Recolouring that
produces a coloured fog, so the prism build inherits the same deficiency.

That is the finding that decided the approach: the detail the simulation cannot
reach is already sitting in the frames the console ships, so the prism is
applied to those instead.

| | |
| - | - |
| `tools/boot-anim/render_boot.py` | Offline procedural renderer. Kept as the reference model and as the `--palette original` comparison harness. numpy plus the standard library, pipes raw frames to ffmpeg. Writes outside the repository by default. |
| `tools/boot-anim/recolor_boot.py` | The shipping path. Reads the console's movie from a path you pass it, moves only chroma, writes an mp4. Same palette, same requirements. |

## What was recovered

### The sequence

`BGLayerNative::BeginBootupSequenceNative` in
`system_ex/app/NPXS40087/eboot.bin` runs three particle patterns and then ends
the welcome animation:

| # | Pattern | Exact evidence |
| - | ------- | -------------- |
| 1 | `coldboot` | selector 0, blob `0xbb0dc0` |
| 2 | `spread_expanded` | selector 1; the preceding `coldboot` blob has one count-24 record naming `coldboot/colorchange/colorchange.` |
| 3 | `spread_expanded_fadeout` | selector 2; the preceding `spread_expanded` blob has the same count-24 string record |

Then `EndWelcomeAnimation`. The renderer is `ParticleBoids`.

The containing particle loader supports seven exact configurations, not only
the three exercised by this sequence. Native function `0x00095920` bounds its
selector to 0-6 and joins relocated name/blob tables with exact byte lengths.
That proves the order `coldboot`, `spread_expanded`,
`spread_expanded_fadeout`, `bottom_camCal`, `bottom_fadeout`,
`initboot_to_spread_no_movie`, `initboot_to_bottom_no_movie`; it does **not**
by itself reveal the particle positions generated by the compute pass. The
36-byte rendezvous entry is now decoded as center, weight, begin/end distance,
and acceleration. The reproducible audit is
`scripts/ps5_particle_patterns.py`; addresses and lengths are recorded in
`docs/ps5-background-native.md`. That audit now also proves the 25 vector
cardinalities, exact element-payload boundary, resource routing, and reflected
field names. Counts 0-7 and field 23 remain intentionally unnamed.

`BackgroundLayer.ColdBootDurationTick` is `60,000,000` at 100 ns per tick, so
the whole sequence is **6000 ms**. That tick is the same unit as a .NET
`TimeSpan` tick, which is why `BootSequenceTimeline.TotalDuration` is literally
`TimeSpan.FromTicks(ColdBootDurationTicks)`.

The full layout walk has now disproved the old acceleration attribution.
`30.0` is in the `coldboot` blob at relative offset `0x1f11`, specifically
field 21, outer record 6, interpolated assignment 1's start value at destination
offset 232. Native routing now proves field 21 targets the large-particle draw
resource table at node `+0x678`, not a compute-simulation resource, so `30.0`
cannot be a rendezvous acceleration. Shader reflection gives destination
offsets 228 and 232 their exact names: `parMinSize` and `parMaxSize`. Coldboot
fades them from 15/30 to zero on large-particle resource index 1 during
seconds 6.5-6.9. `300.0` is in the
`spread_expanded` blob at relative offset `0x1dcc`, specifically field 23,
outer record 0, the middle component of its fixed three-float tail. They are
not the same member in two patterns, neither is a leading blob float, and one
shared `0.1` does not structurally follow both. The desktop renderer no longer
uses those values as forces. It executes coldboot's decoded small-compute
`particleMaxAcceleration1` and `particleCurlSpeedP` ramps, and the two decoded
large-draw count, HSV value, transparency and size records. See
`scripts/ps5_particle_patterns.py` for the checked walk.

### The particle model

From the Ghidra pass recorded in `docs/ps5-background-native.md`:

- A **64-thread compute shader** advects the field with **curl noise**
  (`particleCurlSizeP`, `particleCurlSpeedP`, `particleCurlTimeRateP`,
  `particleCurlSpeedInit`) and accelerates it toward **rendezvous points**
  (`numRendezVousPoints`, `particleRendezVousPoints`,
  `ParticleRendezVousParam: acceleration`).
- **"spread" is the name of a rendezvous set, not of an emitter.** The three
  boot patterns differ in which attractors the field is pulled toward and how
  hard, not in what is emitted.
- The shader carries **two** pattern indices at once, current and previous, so
  a pattern change is a blend rather than a cut.
- Small particles are lit and **depth-of-field blurred by distance from the
  camera**, darkening with distance (`blendDistDarken`, `intensityDistDarken`).
- Large particles are **HSV-tinted bokeh discs** sized between `parMinSize` and
  `parMaxSize`.
- The plate behind them is a **three-stop Catmull-Rom vertical gradient plus a
  coloured light at a fixed off-centre position**, chosen from 37 records at
  `0xbd0ed0`. Records 21-36 put the light at `(-150, 80, 400)`.

### The palettes

All ramp interpolation in this layer is **cubic Hermite / Catmull-Rom, never
linear**. Interior tangents are `0.5 * (p[k+1] - p[k-1])`, the first segment
uses `m0 = p1 - p0` and the last `m1 = p[n-1] - p[n-2]`, and the table is 4320
texels wide. A linear ramp through the same stops is visibly flatter through
the mid-tones. `BootColorRamp` and `catmull_rom_ramp` both implement exactly
that, and `BootColorRampTests` fails if either is replaced by a lerp.

| Ramp | Source | Used for |
| ---- | ------ | -------- |
| Wave preset 2, "blue, brighter", ramp0 of set 0 | table at `0xbd1fd0` | phase 1's motes |
| Wave preset 9, "gold", ramp0 of set 0 | same table | the original palette's motes after the colorchange |
| Plate record 21 | table at `0xbd0ed0` | phase 1's backdrop, prism build only |
| Plate record 9 | same table | the warm backdrop, as authored in the prism build |
| The shared 5-stop alpha array | `0xbd1fd0` | alpha along a particle trail |

Wave preset 9 holds up against the movie. Its stops are a saturated yellow
while the movie's motes read warm white at hue 25, and those reconcile: a mote
is additive and the tonemap desaturates the top end, so the ramp as authored
lands as warm white over a warm plate. Rendered that way our warm hue comes out
at 24 against the reference's 20.

**Neither plate record does.** Both were recorded here as "closest match, not a
traced call site"; the movie says they are wrong, not merely untraced.

- Record 21 carries green at 0.28 of blue. The movie's plate carries it at
  0.041 - at the bloom its per-row median reads 8-bit `(2, 3, 41)` where record
  21 driven to the same blue would read `(5, 21, 41)`. Seven times the green,
  far outside 8-bit noise.
- Record 9 is a yellow at hue 48 with no blue in any stop or in its light. The
  movie's warm plate is a copper at hue 21, linear channel ratio
  1 : 0.57 : 0.39. Solving for record 9 plus any neutral fill drives the plate
  term negative: the movie is redder than record 9 can reach even at zero
  yellow. Its *luminance* run down the frame is consistent; its hue is not.

So `--palette original` takes both plates from the movie's own per-row medians
and keeps record 9 at the 3 % of the warm frame its gradient can account for.
`--palette prism` still runs records 21 and 9 as authored.

The stop positions `0.0, 0.146718, ..., 0.872045, 1.0` recur across almost every
preset. Only the first and last interior positions were read off the firmware;
the four between them are spaced evenly across that span, which the recorded
ones are consistent with.

`scripts/ps5_bg_ramps.py` regenerates the ramp tables from a dump.

## What was measured

The firmware gives the total duration and the phase *order*, not the phase
*boundaries*. Those came from the shipped 3.00 recovery boot movie
(`initial_boot_movie.mp4`, HEVC 3840x2160, 59.94 fps, 13.33 s), swept at 20 Hz
for mean luminance and mean red-minus-blue. Neither the movie nor any frame of
it is in this repository, and nothing here depends on having it.

The movie has no lead-in or lead-out to trim: its first frame is already the
dim plate, its light arrives at 0.584 s and it is black again at 12.963 s. The
correspondence between it and the firmware's 6000 ms is therefore a **linear
time normalisation**, fraction of the movie to fraction of the run. That is an
assumption and it cannot be checked without a capture of the live sequence. It
is at least self-consistent: the blue phase is 63 % of the movie and 63 % of
the firmware's run, so the phase proportions survive the rescale without being
forced to.

| Beat | In the reference | As a fraction | Scaled to 6000 ms |
| ---- | ---------------- | ------------- | ----------------- |
| black hold ends, first seed | 0.584 s | 0.04390 | 270 ms |
| bloom peak | 1.368 s | 0.10280 | 617 ms |
| rendezvous line established | 2.0 s | 0.15004 | 900 ms |
| **colorchange step** | 8.375 s | **0.62830** | **3770 ms** |
| plate leaves black, teal | 8.408 s | 0.63160 | 3790 ms |
| teal at its fullest | 8.559 s | 0.64290 | 3857 ms |
| gold plate has landed | 8.725 s | 0.65540 | 3932 ms |
| **run to black begins** | 11.95 s | **0.89650** | **5379 ms** |
| fully black | 12.963 s | 0.97370 | 5842 ms |

The colorchange is a **step, not a ramp**: in the reference the mean luminance
goes 0.027 -> 0.064 -> 0.188 -> 0.249 in three frames. Scaled, that is a 146 ms
snap, and both implementations treat it that way.

The run to black is the only slow part of the piece: 1.05 s of the reference,
620 ms of ours.

### The teal

The colorchange is not blue to gold. For about 140 ms the **whole plate flashes
teal** and only then does the warm one land - the three middle rows above. The
teal measures hue 203 at saturation 0.82, and plate record 21's own light
colour is `#5BAECE`, hue 197, which over the record's navy gradient lands at
hue 202. So the step reads as blowing out the light term of the plate that is
already there, with the record swapped underneath it a tenth of a second later.
That is how `--palette original` draws it, and it is the one place where the
firmware explained the movie rather than the other way round.

The motes turn gold slightly *before* the plate does: warm sparks are visible
in the dust line from about 0.38 of the run, and the knot is already gold with
a blue core at 0.630 while the background is still black. Neither
implementation models that; both change the motes on the same 146 ms step.

### The warm phase does not stay copper

A second after it lands, the reference's mean saturation falls from 0.35 to
0.13 and the rest of the run is a near-neutral grey lit by the shaft. The
original palette slides its haze and its shaft into an equal-luminance grey
over the 600 ms after the warm plate arrives to match that. Our late grey is
still a warm one, hue 24 to 30, where the reference's carries a violet cast at
hue 322 to 353 - a 50 to 65 degree error, at saturations low enough that it
reads as a subtle wash rather than a miscolour.

## What the prism build changes

**The colour, and only the colour.**

1. **Gold becomes prism.** Preset 9 (gold/yellow) is replaced by an eight-stop
   spectral ramp that sweeps once around the wheel. Eight stops because that is
   the firmware's own colour-array size, so the ramp builder is unchanged.

2. **The change is a dispersion, not a cut.** At the instant of the colorchange
   every particle is still on the blue the sequence has been running for nearly
   four seconds. Over the next 260 ms the spectrum *opens out of that blue*,
   which is literally what a prism does to a beam. `BootPalette.PrismBlue`
   is where the phase-1 blue sits on the prism ramp, and the fan opens from
   there.

3. **The hue is positional, not random.** A particle's place on the spectrum
   comes from its angle around the knot plus a slow rotation, so the field
   reads as a spectral ring flowing around the core. A random hue per mote
   reads as confetti; an ordered one reads as dispersion.

4. **The shaft splits.** The reference already has a shaft of light from above
   and it dominates the warm phase. Ours is drawn as nine spectral wedges from
   one apex; at zero dispersion they sit on the same axis and sum to a plain
   white shaft, and the dispersion term fans them apart.

5. **The plate stays nearly neutral.** It keeps plate record 9's luminance run
   down the frame and takes only a two-point spectral tint. A plate that is
   itself a rainbow reads as mud; the saturated spectrum belongs to the shaft
   and the motes, which are the things a prism actually splits.

The prism build's blue phase is unchanged from what the prism pass shipped, and
that is now known to be some way off the console's: it runs plate record 21,
which the section above shows is not the movie's plate, its bloom peaks at
1.84x its own blue plateau where the movie's peaks at 1.28x, and its core is
whitened to a 0.42 floor where the movie's brightest bloom pixels stay a
saturated blue. `--palette original` corrects all three against the movie.
Where a correction is not a matter of taste it is applied to both: the first
seed of light is at 0.0439 of the run, not 0.03376, so `SEED_MS` is 270 ms.

## The offline renderer

```
python tools/boot-anim/render_boot.py --ffmpeg <path to ffmpeg>
```

1920x1080, 60 fps, 6.0 s in the console's own palette, plus a contact sheet.
Pass `--palette prism` for the substitution. The output path defaults
**outside the repository** so a render cannot land in git by accident. Useful
flags:

| Flag | |
| ---- | - |
| `--palette original\|prism` | `original` is the console's own gold and is the default; `prism` is the substitution |
| `--out`, `--contact` | where to write |
| `--width`, `--height`, `--fps` | a 640x360 preview renders in about twenty seconds |
| `--layers plate,shaft,ribbons,dust,bokeh,core,bloom` | isolate one layer while tuning, the same idea as `ShellBackground.DiagnosticIsolateLayer` |
| `--exposure` | for looking at a layer that is too dim to judge on its own |
| `--seed` | the field is deterministic |

It works in linear light and encodes sRGB at the end. The ramp dumps are 8-bit
sRGB renderings of the stored floats, so they are decoded back to linear before
anything is added to anything; the plate records are stored linear and are used
as authored.

## The recolour, which is the path that ships

Simulating the sequence reproduces its clock and its exposure and does not
reproduce its image: 22 % of the reference's detail through the blue phase,
34 % through the warm one. The console ships the piece as a real movie, and
every ribbon, mote and bokeh disc that the simulation loses is already in those
frames. So the shipping path takes the frames as they are and moves only their
chroma.

```
python tools/boot-anim/recolor_boot.py --source <your dump>/initial_boot_movie.mp4 \
    --out <somewhere outside the repo>/prosperismo_boot_recolored.mp4
```

The source is opened read-only and `--source` is required, so the tool runs
against a user's own dump and nothing about the movie is embedded here.

**What moves.** From the moment the warm colour lands, a pixel's hue is
replaced by one chosen from where that pixel sits relative to the knot of
ribbons. Luminance is untouched - the work is done in Oklab, so `L` survives
exactly and so does every edge in the source.

**Why it is a dispersion and not a tint.**

1. **Hue is a function of position, never a constant offset.** It sweeps one
   full turn of the prism ramp around the knot, plus a term in radius, so a
   ribbon arcing past the core crosses several hues along its own length. No
   hue-rotate filter can produce that.
2. **Chroma is suppressed near the knot and lifted away from it**, so the core
   stays near-white and the spectrum opens outward from it.
3. **The prism splits the light, not the wall.** The dispersion is weighted by
   a structure mask - luminance minus a wide blur - so the ribbons, motes and
   bokeh take the full spectrum and the smooth plate takes a fifth of it. The
   first cut of this weighted everything equally and painted large flat bands
   of colour across the background, which is exactly what a gel filter looks
   like. The background's chroma comes *down* instead, to a near-neutral room
   that the spectrum in front of it can read against.
4. **The first act is left as authored.** The blue is the console's blue and
   the ~140 ms teal beat before the warm landing is the console's too. The fan
   opens over about half a second once the warm colour has arrived, so the
   spectrum is seen to open out of the sequence rather than replacing it.

**Two things that had to be got right or the frame tears.**

- *The ramp has to close.* As authored the eight prism stops run red at 0.0 to
  magenta at 1.0, which is a strip, not a wheel. A field that wraps through it
  has a discontinuity, and because the fan's position is an angle plus a
  radius, that discontinuity draws a spiral across the frame.
  `cyclic_prism_stops` respaces the same eight colours onto the first seven
  eighths and repeats the first at the end.
- *The blend has to happen in the a/b plane, not around the hue circle.* Where
  the target hue is opposite the source's, the shortest way round flips from
  one direction to the other along a locus across the frame, and a partly
  applied flip is a hard seam - the same seam, in the same place, that closing
  the ramp did not fix. A straight line between the two colours has no such
  choice to make, and where they really are opposites it passes through
  neutral, which is what a colour does anyway when it changes sides.

**Knot tracking.** The fan needs to know where the light is coming from. The
brightest thing in the warm phase is the shaft entering off the top-left
corner, so a plain luminance centroid slides into that corner and stays there.
Subtracting a wide blur removes the shaft and the plate - both are smooth - and
leaves the ribbons and motes, whose centroid is what the fan is centred on. The
track is smoothed over about half a second; a fan that jitters frame to frame
reads as a crawling texture.

## The in-app layer

The GUI now attaches `BootIntroOverlay` at startup and renders the procedural
`BootIntroField`/`BootIntroCompositor` path. It is a visualization of the
recovered sequence, duration, palettes and broad GPU model; it is not execution
of Sony's particle shaders or position buffer. The record-to-resource map is now
decoded, and `Ps5ColdBootLargeDraw1Evaluator` exactly executes the second
large-draw bank's 6.0-8.5 event state. The overlay still places those draw values
on procedural carrier motes, so its pixels remain experimental. The authored
0..8.5 pattern clock is currently mapped linearly onto the managed 6000 ms boot
duration; that time-base relationship is not yet proven.

## Still unknown

- The pattern blobs at `0xbb0dc4` onward now have exact event/resource routing,
  many reflected field names, and an executable resource-state sampler. The
  36-byte rendezvous entry layout is recovered. The full 29,760-byte
  `particle_c` section decodes to 5,024 instructions and translates to SPIR-V
  with the recovered 64x1x1 firmware launch registers. Its exact 6.0-second
  spawn-window state now runs on Vulkan and generates 40 native
  `particleProperties` records. Constructor `0x94020` now supplies the exact
  two zero-based shuffled ID buffers, including their continuous native RNG
  state; the active first group uses the first permutation. The point sets still
  displayed by both procedural visualizers are ours; they have not yet been
  replaced by this native readback. Both original large-particle draw
  stages now translate, validate, link on the host driver and consume the GNF
  assets in an off-screen probe. After fixing the property selector and flat
  `v_interp_mov_f32` input, a continuous t=6.5 run now renders 26 native
  billboards and changes 1,449,449 pixels. That visible frame is firmware-shader
  output. The managed shell can now consume a generated animated two-bank
  cache; the separate procedural boot overlay remains procedural.
- `ParticleBoids`' own parameters were never chased. The emission counts in the
  procedural renderer (260 trail heads, 14,000 motes, 96 bokeh discs) are ours,
  chosen to keep a Python frame under a second, and they are the reason that
  reproduction is a fog: the reference needs roughly an order of magnitude
  more. This is the gap the recolour path sidesteps rather than closes.
- Which of the 21 wave presets and 37 plate records the cold boot selects is
  not traced. Preset 2 and preset 9 hold up against the movie; records 21 and 9
  do not, as above, so the plate the cold boot actually selects is still
  unidentified - it may not be in this table at all.
- Whether the movie and the live sequence share a time base. The linear
  normalisation used here is an assumption, not a measurement.
